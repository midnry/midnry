## 1. Where it was verified

There is **no staging or preview service**. `render.yaml` defines one free web service, deployed
from `main`, and one free database. This environment has **no AI, email or Paystack credentials**.
The closest production-like setup available was used instead:

- **Build:** the release commit's production build, made exactly as Render makes it
  (`VITE_AUTH_ENABLED=true NITRO_PRESET=render npm run build:render`).
- **Start:** started exactly as Render starts it (`npm start`: the production migration script,
  then the server).
- **Database:** an empty, throwaway local **PostgreSQL 16** database. All 25 migrations were
  applied by the production script (recorded in its `_migrations` table).
- **Settings:** `NODE_ENV=production`, sign-in on, and an admin email for Pass access.
- **Data:** synthetic accounts only (`*@example.test`). No real customer data was used, and no
  card was charged.
- **Paystack:** replaced by the repository's local stand-in (`scripts/qa/mock-paystack.mjs`). This
  exercises Midnry's side of checkout only.
- **Browser:** headless Chromium at 1280×900 and at a **phone-sized 390×844 touch viewport**. That
  is not a real phone, and **nothing was tested in iPhone Safari**.

Differences from real production:

- The site was served over plain HTTP on 127.0.0.1, not HTTPS through Cloudflare.
- The database was local Postgres 16, not Render's.
- There were no AI, email or Paystack keys.
- Render's own sign-in origin settings (`RENDER_EXTERNAL_URL`) were not set.

## 3. Regression found and fixed during this verification

**One account's unsaved change could be saved into another account.** The situation: a page opened
by account A still has an unsaved change (offline, retrying), and account B then signs in on the
same browser. A's next retry went out with B's session, so it **saved A's text into B's document**.
This was reproduced: A's Emergency card text landed on B's card. The Writing studio's draft retry
had the same flaw.

- **Not introduced by this batch:** the save requests never said which account they were for, and
  production `df7e52c` has the same code.
- **Fixed in `19e4d39` anyway:** this release promises account isolation, and the fix is small.
- **How it works now:** every save names the account its page was opened for, and the server
  refuses a mismatch. The page then stops saving and keeps the change in that browser for the
  original account only. A panel explains this ("Another account is signed in now").
- **Pages opened before the release** send no account name, so they keep the old behaviour until
  they are refreshed.

## 6. Rollback plan

- **Fast rollback (recommended):**
  1. Render dashboard → the `midnry` service → Deploys → the previous deploy of `df7e52c` →
     "Rollback". No git change is needed. It takes about the time of a restart.
  2. Then put the code back the same way: `git revert -m 1 <the release merge>` on `game-look`,
     and push to `main` when ready. Never force-push `main`.
- **Data compatibility:**
  - This release adds **no database migrations**, so rollback needs no database work.
  - **One caveat:** the old Invoice code does not know the new "How to pay" field. After a
    rollback, the next Invoice save by anyone who filled it in drops their bank details, so they
    would need to type them again. Invoices, quotes, clients and notes are unaffected.
  - **Recovery copies in browsers:** copies saved with the new reasons are ignored by the old code,
    and the change stays only on the person's own browser. Nothing crashes.
  - **Saves after a rollback:** they no longer carry the account name. The old server ignores the
    extra field, so nothing breaks.
- **When to roll back:**
  - A page error on `/apps`, `/apps/invoice`, `/apps/ledger` or any kit.
  - Saving fails for any app on a normal connection.
  - Sign-in fails.
  - **For anything narrower, prefer a fix forward.** One example is a wrong message in one kit.
    That keeps the account-isolation fix live.
